1. Introduction
1.1 Purpose
This SRS is the complete design baseline for Lex — a unified legal AI platform that collapses three previously
separate systems (Legal AI Copilot, Legal Due Diligence Agent, Legal Action Agent) into one product with one entry
point, one data model, one orchestration layer, and one frontend. This document supersedes all prior per-system
specifications.

1.2 Scope
Lex enables lawyers and legal professionals to upload a deal folder of contracts, amendments, and side letters;
state a goal in plain language; and receive grounded legal analysis, cross-document reasoning, or executed legal
workflows — depending on what the goal requires. The system determines which capabilities to invoke. The lawyer
never selects a mode.
The system comprises: a unified FastAPI backend; a LangGraph master orchestrator; three capability layers
(retrieval, graph intelligence, action); a document intelligence pipeline that runs once per document and is shared
across all layers; and a Next.js frontend with an adaptive results interface.

1.3 The Core Design Decision
The central architectural decision of Lex is that document intelligence is separated from goal execution. When a
document is uploaded, the system immediately builds a complete intelligence package: clause-boundary chunks,
dual embeddings, defined terms registry, cross-reference graph, and deadline registry. This runs asynchronously
and completes before the lawyer submits any goal.
Every subsequent goal submission against that document consumes this pre-built intelligence. There is no
per-query ingestion. There is no pipeline-specific indexing. One document, one intelligence package, infinite goals.
The second core decision is intent-based routing. The master orchestrator classifies the lawyer's goal into one of
three intents — ANALYZE, REASON, ACT — and composes exactly the capability layers that intent requires.
Unneeded layers do not run. Latency scales with what the goal actually needs, not with what the system is
theoretically capable of.

4.2 The Master Orchestrator
The master orchestrator is a LangGraph state machine that owns the full lifecycle of a goal submission. It is the
single brain of the unified system — replacing three separate planners with one composable coordinator.
Orchestrator responsibilities:
→ Receive goal submission, retrieve workspace context and document intelligence summary
→ Classify intent (ANALYZE / REASON / ACT) with a confidence score
→ If confidence < 0.80: trigger ambiguity gate — show classification + ask for confirmation
→ Select capability layer path based on confirmed intent
→ Build execution plan: ordered LangGraph nodes for this intent
→ Execute nodes, checkpoint state to PostgreSQL at every transition
→ Manage HITL gates (ambiguity gate + approval gate for ACT)
→ Surface result to frontend through unified result schema

4.3 Intent Classification & Routing
Intent classification is the first node in every workflow execution. It is a structured LLM call — Claude Sonnet
receives the goal text, the workspace document manifest, and any pre-flagged conflicts from the defined terms
registry, then returns a structured classification object.

4.4 Ambiguity Resolution Gate
When intent classification confidence is below 0.80, the orchestrator pauses before dispatching any capability layer
and presents its best guess to the lawyer.
The interface shows:
→ The system's classification: 'I read this as a REASON goal — find risks across the deal folder'
→ A brief plain-language explanation of what that means it will do
→ Two responses: 'Yes, proceed' and 'No, change it' (which reveals the other two intent options as buttons)
The lawyer's selection is recorded in the WorkflowExecution as intent_confirmed_by_human=True with the original
classification and confidence preserved for audit and research purposes. This data feeds the intent classifier's
improvement loop.

If the lawyer does not respond within 10 minutes, the ambiguity gate expires and the workflow returns
status=AWAITING_INTENT_CONFIRMATION. No capability layer has run. No resources consumed beyond the
classification call.

4.5 Workspace Sessions
A workspace session is the primary context object — it binds a lawyer to a set of documents for a working period.
Sessions persist across multiple goal submissions. A lawyer working on a deal folder creates one session for that
folder and submits as many goals as needed within it.

4.6 LangGraph State Machine
Node execution paths per intent:
ANALYZE path:
intent_node → retrieval_node → synthesis_node → result_node
REASON path:
intent_node → retrieval_node → graph_expansion_node → defined_terms_node
→ contradiction_node → findings_node → escalation_node → result_node
ACT path:
intent_node → retrieval_node → graph_expansion_node → defined_terms_node
→ contradiction_node → draft_node → approval_node
→ [on approve] execute_node → [on success] audit_node → result_node
→ [on reject] revision_node → draft_node (loop, max 3)
→ [on failure] recovery_node → [retry | compensate | escalate]
Ambiguity gate (any path, when confidence < 0.80):
intent_node → ambiguity_gate_node → [confirmed] → path selection
→ [expired] → AWAITING_INTENT_CONFIRMATION

4.7 Capability Layer Contracts
Each capability layer exposes a typed interface to the orchestrator. Layers are independent Python modules. The
orchestrator calls them by interface, not by implementation — swapping a layer does not require orchestrator
changes.
class RetrievalLayer(Protocol):
async def search(self, query: str, workspace_id: UUID,
session_id: UUID, mode: RetrievalMode) -> RetrievalResult: ...
class GraphIntelligenceLayer(Protocol):
async def analyze(self, chunks: list[Chunk], workspace_id: UUID,
goal: str) -> GraphAnalysisResult: ...
class ActionLayer(Protocol):
async def draft(self, context: ActionContext) -> DraftResult: ...
async def execute(self, action: ApprovedAction) -> ExecutionResult: ...

FR-WS-03

Document intelligence pipeline

Baseline

Trigger

Celery task dispatched after FR-WS-02 for new (non-duplicate) documents

Stage 1

Parse: PyMuPDF (digital PDF), GeminiOCR (scanned PDF), python-docx (DOCX). Detect document
type.

Stage 2

Chunk: clause-boundary chunker using spaCy legal NER + regex header detection. Respect section
boundaries. No sliding-window fallback until after clause detection fails. Chunk size: clause-level (not
fixed token). Parent context window: 2,000 chars.

Stage 3

Embed: OpenAI text-embedding-3-large (dense primary) + legal-bert (dense secondary). Stored as
named vectors in Qdrant. BM25 sparse index also built. All three available for RRF fusion.

Stage 4

Defined terms: spaCy + LLM-assisted extraction of all definitions sections. Per term: name, definition
text, source document, page, clause reference. Stored in DefinedTermsRegistry. Cross-document
conflict detection runs after all documents in workspace are processed.

Stage 5

Cross-reference graph: regex + LLM hybrid parser. Regex catches standard patterns (Section X.X,
clause X.X(Y)). LLM catches natural language references ('as set forth in the Master Agreement',
'subject to the terms of the SOW'). Nodes = clauses. Edges = references. Written to Neo4j.

Stage 6

Deadline extraction: LLM extracts all temporal obligation language. Resolves relative dates against
execution date if available. Flags RELATIVE_UNRESOLVED if execution date missing. Writes to
DeadlineRegistry. Conflict detection if two clauses define conflicting deadlines for same obligation.

Completion

Document.status = READY. Workspace intelligence summary updated. Frontend polling receives
status update.

On failure

Document.status = FAILED with error_message. Reprocess endpoint available. Each stage failure is
independent — partial intelligence packages are stored and flagged.

5.4 ANALYZE Execution Path
FR-ANA-01

Mode

Retrieval execution

Baseline

Hybrid by default (dense + BM25 sparse, RRF fusion in Qdrant). Session carries user preference
override.

Scope

Session document subset if specified. Otherwise all READY documents in workspace. Never crosses
org boundary.

Named vectors

Query run against both text-embedding-3-large and legal-bert vectors independently. Results fused
via RRF before reranking.

Reranker

Cohere Rerank v3. Instrumented: negation pair score, top-1 stability under premise shift, and
premise-match score logged to ResearchLog on every call.

Fallback

If < 3 relevant chunks retrieved (relevance_score > 0.6): return UNDETERMINED — do not
synthesise. Surface as escalation type INSUFFICIENT_COVERAGE.

FR-ANA-02

Answer synthesis

Baseline

Inputs

Retrieved chunks + reranked scores + goal + workspace context

Processing

Claude Sonnet with explicit CoT prompt: (1) extract key claims step by step, (2) verify each claim
against source chunk, (3) synthesise final answer. Temperature=0.

Output schema

AnalyzeResult: answer (str), confidence (float), source_citations (list[Citation]), retrieval_mode_used,
chunks_used_count, undetermined (bool), undetermined_reason (str|None)

Faithfulness

Every claim in answer must map to a retrieved chunk. Hallucinated claims must be absent — prompt
enforces this with negative examples. Faithfulness score logged to ResearchLog.

5.5 REASON Execution Path
FR-RSN-01

Graph expansion

Baseline

Trigger

After retrieval, before synthesis — every retrieved chunk is expanded

Processing

For each retrieved chunk: query Neo4j for outbound references (clauses this chunk cites) and

Add to synthesis context with reference_type label.

Depth

Two hops maximum. Beyond two hops, include clause_id reference in output but do not pull full text.

Performance

Neo4j queries batched per chunk. Total graph expansion adds < 3s to REASON path p95.

Output

FR-RSN-03

Per-task findings

List of DefinitionalConflict objects attached to each Finding.

Findings generation & contradiction detection

contradictions

same obligation but make conflicting claims — flag as Contradiction with source_a, source_b,

FR-ACT-01

Inputs

Action detection

Baseline

Goal + retrieval context + graph analysis result + DefinedTermsRegistry conflicts + DeadlineRegistry

5.7 Approval Gate System
The approval gate system applies to ACT path only. Full spec below.

FR-GATE-01

State persistence

Issue approval request

Baseline

WorkflowExecution checkpointed to PostgreSQL (status=AWAITING_APPROVAL,
langgraph_checkpoint serialised). All LangGraph state recoverable on restart.

Token

HMAC-SHA256(workflow_id + action_id + org_id + expires_at, org_scoped_secret). Stored hashed.

Notification

FR-GATE-02

Process approval response

Baseline

On reject

ApprovalRequest status=REJECTED. rejection_reason required (min 20 chars). status=REVISING.
Revision node enqueued with rejection_reason.

Audit

Every approval event written to AuditLog before re-enqueuing. No exceptions.

TTL, expiry, re-issue

Baseline

Default TTL

72 hours (configurable per org, range 1–168 hours)

Expiry scan

Celery Beat every 15 minutes. Expired gates: status=EXPIRED, status=ESCALATED, Admin
notified.

Re-issue

Admin may re-issue for ESCALATED workflow. New token, TTL reset, history preserved.

Rule

Transient failure

Permanent failure

Log TOOL_CALL_FAILED. Escalate. No compensation.

Baseline

— idempotent

— non-idempotent

5.10 Deadline Registry & Scanner
FR-DEAD-01

Processing

Deadline extraction at ingestion

Baseline

LLM extracts all temporal obligations: description, raw date expression, resolved absolute date (if
computable), obligation_type (RESPONSE|FILING|NOTICE|PAYMENT|OTHER), source clause

Conflicts

Two clauses defining conflicting deadlines for same obligation: CONFLICTED status,

obligation, different deadlines across documents — flagged immediately.

Baseline

FR-DEAD-02

Celery Beat scanner

Schedule

Every 15 minutes

Logic

For all ACTIVE deadlines: (1) days_remaining = deadline_date - now(). (2) days_remaining <= 1:
urgency=0.95. (3) 1 < days_remaining <= 3: urgency=max(current, 0.85). (4) days_remaining < 0:
OVERDUE — immediate Admin notification. (5) Push urgency updates to linked Actions in ACT
workflows. (6) Re-notify approver if linked action in AWAITING_APPROVAL and urgency >= 0.85.

5.12 Research Instrumentation
Research instrumentation runs on every retrieval call, regardless of intent path. This is the passive data collection
mechanism for the negation-aware reranking paper and future classifier improvement work.

FR-RES-01

Reranker negation

Per-retrieval research logging

Baseline

For each reranked chunk pair (original + negated variant if synthetic negation is enabled):
score_original, score_negated, delta. Feeds negation sensitivity analysis.

Top-1 stability

On queries with premise variants: top-1 chunk identity across variants logged. Measures reranker
sycophancy.

Faithfulness

After synthesis: LLM self-evaluation of whether every claim maps to a retrieved chunk. Score
0.0–1.0. Logged per WorkflowExecution.

Intent data

Every classification logged: goal_hash (SHA-256, not raw text), intent, confidence, confirmed_intent,
lawyer_changed_intent (bool).

Storage

ResearchLog table — separate from AuditLog. No PII. goal_hash not reversible. Exportable for paper
experiments.

13. Glossary
Term

Definition

Workspace

A named deal folder — documents + user context. Primary unit of work in Lex.

Goal

A plain-language statement from the lawyer. The system's input.

Intent

The orchestrator's classification of a goal: ANALYZE, REASON, or ACT.

Ambiguity gate

A durable pause when intent classification confidence < 0.80. System shows its best guess,
lawyer confirms or changes.

Document intelligence

The complete set of artifacts built at ingestion: chunks, dual embeddings, defined terms,

package

cross-reference graph, deadline registry entries.

Capability layer

One of three composable modules: Retrieval, Graph Intelligence, Action.

Named vectors

Qdrant's per-point multiple vector support — text-embedding-3-large and legal-bert stored
on the same point, queried independently and fused via RRF.

RRF

Reciprocal Rank Fusion — fusion algorithm combining dense and sparse retrieval rankings.

Graph expansion

Pulling Neo4j-referenced clauses into retrieval context — dependency-aware retrieval.

Defined terms registry

PostgreSQL table of all terms defined across workspace documents, with cross-document
conflict detection.

Deadline registry

PostgreSQL table of time-bound obligations extracted at ingestion. Scanned by Celery Beat
every 15 minutes.

HITL

Human-in-the-loop — any workflow step requiring a human decision before continuation.

Approval gate

Durable ACT-path HITL pause requiring explicit lawyer sign-off. HMAC-gated,
TTL-enforced, single-use token.

Saga

Distributed transaction pattern: each tool call has a compensation action; used for
non-idempotent failure recovery.

Idempotency key

SHA-256(workflow_id + action_id + tool_name + attempt_number) — prevents
double-execution on Celery retry.

UNDETERMINED

Response mode when < 3 relevant chunks retrieved. Never synthesise without sufficient
evidence.

UNCOMPENSATABLE_FAIL

Permanent failure of a non-idempotent tool where compensation is not supported. Always

URE

escalates immediately.

ResearchLog

Separate table from AuditLog. Stores retrieval metrics, reranker scores, faithfulness scores,
intent classifications. No PII. Exportable for research.

LangGraph

Orchestration library managing the workflow as a directed graph of Python functions with
durable PostgreSQL-backed state.

Prompt hash

SHA-256 of exact prompt text sent to LLM. Stored in AuditLog. Full prompt archived to R2.
Enables post-hoc verification.

PARTIAL intelligence

A document whose intelligence pipeline completed some but not all stages. Downstream
layers use available stages; degraded mode noted in results.
